## 0. 选题定位

**一句话：** 逛 GitHub 时到处能看到的 `.claude`、`AGENTS.md`、`SKILL.md`，打开来**不是代码，是一封封用 Markdown 写给 AI 的信**。Markdown 并不是 AI 的「底层」，底层是 token；它是**人和模型两边都能直接读懂的那种格式**，所以成了人和 AI 之间的共同语言。

**为什么不说「底层逻辑」：** 模型内部只处理 token（一串数字），它从来没「看见」过加粗（实测：`**` 只是一个 token，F-8）。把 Markdown 说成底层逻辑，懂行的观众会在评论区纠错。把纠正本身做成反转更好：

> 你以为：AI 天生就懂 Markdown，它是 AI 的底层逻辑
> 其实：它是 2004 年为写博客的人设计的格式，碰巧人和机器都读得懂，又被训练、被界面、被省钱一步步推成了 AI 的通用语

**受众：** 学 AI、用 AI 写代码、逛 GitHub 的人（频道「vibe」的核心受众）。比「普罗大众真实困惑」窄，但对这群人是天天在用、却没想过为什么的东西。
**扩圈的一拍：** 从 AI 聊天框复制到微信，满屏 `**` 和 `###`（F-9）。几乎所有用过 AI 的人都遇到过，放在中段，让非程序员也能接住。

## 1. 核心机制（讲给自己听的版本）

### 1.1 这些 .md 文件是什么

| 文件 / 目录 | 谁在用 | 里面装的 |
|---|---|---|
| `CLAUDE.md` | Claude Code | 项目说明：怎么构建、代码风格、注意事项 |
| `AGENTS.md` | Codex、Cursor、Gemini CLI、Copilot、pi 等 | 同上，跨工具的通用版（F-5） |
| `.claude/skills/*/SKILL.md` | Claude Code | 一项「技能」：什么时候用、怎么做 |
| `.codex/`、`.pi/` | Codex CLI、pi | 配置 + skills，里面的说明文件同样是 SKILL.md / AGENTS.md（F-6） |
| `.cursor/rules/*.mdc` | Cursor | 规则，Markdown 加一段头信息 |
| `.github/copilot-instructions.md` | GitHub Copilot | 给 Copilot 的项目说明 |
| `llms.txt` | 网站 | 给 AI 读的网站导览，格式是 Markdown（F-7） |

**规模（GitHub 代码搜索，2026-10-18 实测，F-4）：**
- `SKILL.md` 约 **630 万**个文件，`AGENTS.md` 约 **112 万**，`CLAUDE.md` 约 **84 万**
- `.claude/` 目录里约 301 万个文件，其中 `.md` 约 193 万，**超过六成**；`.json` 只有约 31 万
- `.codex/`、`.pi/` 目录里，`.md` 也都占一半左右

**反转句：** 过去给软件下命令，要写代码、写 JSON 配置。现在给 AI 下命令，写的是一篇带 `#` 和 `-` 的短文。

### 1.2 为什么偏偏是 Markdown：四个原因

1. **它生来就是「不渲染也能读」的（2004）**（F-1）
   John Gruber 设计 Markdown 时的首要目标是可读性：一份 Markdown 文档应该以纯文本的样子就能直接发布，看不出被标记过。语法的最大灵感来自纯文本电子邮件。Aaron Swartz 对语法设计贡献很大。
   → 人不渲染也看得懂，机器不渲染也解析得了。这是它能当「共同语言」的根。
2. **AI 是读着它长大的**（F-2，只讲定性）
   预训练语料里有大量 GitHub README、技术文档、论坛帖，这些多半是 Markdown。**没有可靠的「占比多少」数字，片中不给数字。**
3. **AI 被要求、也被奖励用它说话**（F-3a、F-3b）
   - OpenAI 的 Model Spec 写明：除非另有说明，回答应当用 **Markdown（加 LaTeX 扩展）** 格式。
   - Chatbot Arena 2024 年的「风格控制」研究：回答里的列表、标题、加粗越多，越容易被用户投票选中（系数都是正的，但远小于「回答长度」的影响）。人更爱点结构清楚的回答，于是模型越来越爱用 Markdown。
4. **它便宜**（F-8，我们实测）
   同一份「周末计划」（标题 + 三条清单 + 一句重点），用 GPT-4o/GPT-5 的分词器（o200k_base）数 token：

   | 格式 | 字符 | token（GPT，o200k） | token（千问 Qwen3） |
   |---|---|---|---|
   | 纯文本 | 27 | 23 | 17 |
   | **Markdown** | 41 | **28** | **30** |
   | YAML | 64 | 35 | 38 |
   | JSON | 99 | 48 | 42 |
   | HTML | 98 | **54** | **48** |

   两种分词器结论一致：在能表达结构的格式里，Markdown 最省。GPT 分词器下，它只比纯文本多 5 个 token；同样的结构用 HTML，token 差不多翻倍（千问下是 1.6 倍）。片中用 GPT 那一列，千问作为旁证。`**重点**` 是 3 个 token，`<strong>重点</strong>` 是 6 个，`<h1>标题</h1>` 是 8 个。

### 1.3 模型眼里的 Markdown

- `**重点**` 在模型里是 `**` · `重点` · `**` 三块（F-8）。模型从来没见过「加粗」，它只见过两个星号。
- 加粗是你的聊天界面画出来的。所以把回答复制到不渲染 Markdown 的地方，比如微信，就会冒出满屏星号和井号（F-9）。
- 这一拍连接了「程序员的 .md 文件」和「普通人的日常体验」。

### 1.4 推导出的结论（片子的主张）

> Markdown 不是 AI 的底层逻辑，它是人和 AI 之间的「普通话」：
> 人不用渲染也能读，模型不用渲染也能懂，又短又省 token。
> 所以 AI 的说明书、记忆和技能，最后都写成了 .md。

**能带走的一句：** 给 AI 写提示词、写说明，用 `#` 分段、用 `-` 列要点，它更容易抓住结构。**分寸：** 不能说「用 Markdown 效果一定更好」（F-10）。

## 3. 流行误区与坑

| 说法 | 实际 | 处理 |
|---|---|---|
| 「Markdown 是 AI 的底层逻辑 / 底层语言」 | 底层是 token；Markdown 是常用的输入输出格式 | 当成反转来讲：「它不是底层，是普通话」 |
| 「用 Markdown 写提示词，AI 效果更好」 | He 等（2024）：格式确实影响结果，GPT-3.5 最多差 40%；但**没有一种格式总是最好**，有的任务里 JSON 胜过 Markdown（F-10） | 只说「把结构写清楚，它更容易抓住」，不说「Markdown 最强」 |
| 「训练数据里 X% 是 Markdown」 | 没找到可靠数字 | **不给数字** |
| 「AI 是专门为 Markdown 设计的 / Markdown 是为 AI 发明的」 | 2004 年为写博客的人设计，比 ChatGPT 早 18 年 | 正好用来做「出身」反转 |
| 「所有 AI 都默认输出 Markdown」 | OpenAI 的推理模型（o1-2024-12-17 起）在 API 里默认**不**用 Markdown；语音模式也不适合 | 片中说「聊天界面里」「大多数」，不说「所有」 |
| 「Markdown 让人投票更多 X%」 | Arena 的文章只给了回归系数，没给百分比；长度才是主因 | 不给百分比，只说「更容易被选中」 |
| GitHub 搜索数字 | API 的 total_count 是估算值，只索引默认分支，会随时间变化 | 片中写「约」，并注明「2026 年 10 月」 |
