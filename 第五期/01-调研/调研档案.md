## 0. 选题定位与风险提示

**一句话：** 你在修图软件里拖的每一个滑块，本质上都是在对几千万个数字做同一道算术题。这些数字为什么是"三个一组"，要从人眼说起。

**"第一性原理"的推导链（全片骨架）：**

> 光 → 人眼只有三种感色细胞 → 所以三个数就能"骗"出一种颜色 → 一张照片 = 几百万个"三个数" → 每个滑块 = 一条"把这个数变成那个数"的规则 → 滤镜 = 把这些规则打包成一张表

**卖点：** 看完之后观众会觉得这些滑块自己也能发明出来。脚本可以反复用"如果你是设计师，想让照片更亮，你会怎么改这三个数？"来设问，下一拍再揭晓。

**为什么适合这个账号：**
- 人人都调过色，几乎没人知道滑块背后在做什么，属于"原来如此"型知识
- 看完能用上（拍照建议），观众有收藏的理由
- 天生适合视频：像素放大、数字跳动、滑块拖动都是看得见的

**风险：**

1. **AI 生成照片要标识。** 《人工智能生成合成内容标识办法》2025 年 9 月 1 日起施行；抖音同日上线 AI 内容标识，发布时可以主动声明"由 AI 生成"，没声明的会被检测并打上"疑似使用了 AI 生成技术"的提示，严重的还会被取消收益。**建议发布时主动勾选声明。** 这期照片是写实风格，比第四期的插画更容易被检测到。
2. **容易拍成又一个调色教程。** 每个技巧都要从原理推出来，不要罗列操作步骤。
3. **简化的分寸。** 真实软件里的"亮度"不是简单的加法，"对比度"也不是简单的直线拉伸，用的都是更柔和的曲线。上屏统一说"最简单的做法"，或者直接展示曲线，不要说"软件就是这么算的"。
4. **屏幕颜色。** 观众是在手机屏幕上看这期视频的。"屏幕上没有黄色的点"这一段对 LCD 和 OLED 都成立，但子像素的排列方式不同（见核实表），画面上画成通用的红绿蓝条纹或圆点就行，不要画成某个具体品牌的屏幕。

## 1. 一句话讲清 + 类比库

| 概念 | 一句话 | 生活类比 |
|---|---|---|
| 颜色 | 眼睛里三种感光细胞各自被刺激了多少 | 三个音量旋钮，混出所有声音 |
| 像素 | 照片上最小的一格，里面存着 R、G、B 三个 0–255 的数 | 十字绣的一格 / 马赛克的一块瓷砖 |
| 亮度 | 三个数一起变大或变小 | 整体调高音量 |
| 过曝 | 数字顶到 255，超出的部分被截掉，信息永久丢失 | 杯子满了，多倒的水洒了，倒不回来 |
| 对比度 | 以中间灰为轴，亮的更亮、暗的更暗 | 把一根橡皮筋从中间往两边拉 |
| 饱和度 | 一个颜色离同样亮度的灰色有多远 | 往颜料里兑灰水，越兑越灰 |
| 白平衡 | 给 R、G、B 各乘一个系数，把"本该是白的东西"拉回白色 | 戴着黄色墨镜，摘下来之前先在脑子里减掉黄色 |
| 曲线 | 输入一个数，输出一个数的对照图；前面所有滑块都是曲线的特例 | 换算表 |
| 滤镜 / LUT | 一张"每个颜色变成什么颜色"的查找表 | 字典：查到这个词，就换成那个词 |
| 直方图 | 每种亮度有多少个像素 | 全班成绩分布图 |

## 2. 核心原理（按推导链顺序）

### 2.1 颜色不在光里，在眼睛里 ★★★（第一性的起点）

- 人眼负责看颜色的是视锥细胞，正常人有**三种**：S（短波，峰值约 420–440 nm，偏蓝）、M（中波，约 534–545 nm，偏绿）、L（长波，约 564–580 nm，偏黄绿）。峰值因人、因测量方法略有不同。（教材 / 百科）
- 大脑看到的"颜色"，只是这三种细胞各自被刺激了多少，相当于**三个数**。
- 推论：两束光谱完全不同的光，只要让三种细胞的反应一样，看起来就是同一种颜色。这叫**同色异谱**（metamerism）。
- **屏幕上的黄色**：屏幕没有发出黄光，而是红光和绿光同时亮，刺激眼睛的方式恰好跟黄光一样。凑近看屏幕，只有红绿蓝三种小点。★★★ **这是最好的钩子**：观众可以自己拿放大镜或手机微距去验证。
- 所以 RGB 不是人为规定的，而是"人眼只有三种细胞"推出来的。（注意：屏幕的 RGB 三原色和三种视锥的峰值并不一一对应，上屏不要画"红色细胞 / 绿色细胞 / 蓝色细胞"。可以画成"三种细胞"，也可以叫"短波、中波、长波"。）

### 2.2 照片 = 几百万个"三个数" ★★★

- 像素（pixel）就是 picture element，照片上最小的一格。
- 常见照片每个通道用 8 位存储，即 0–255，共 256 级。三个通道组合起来有 256³ = **16,777,216** 种颜色，也就是常说的"1670 万色"。（自算）
- 一张 1200 万像素的手机照片 = 1200 万格 × 3 个数 = **3600 万个数字**。（自算）
- 画面：把主图一路放大，变成马赛克，再放大到一格，格子里出现三个数。

### 2.3 意外的一层：相机里每个像素只测了一种颜色 ★★★（反转素材）

- 绝大多数相机和手机的传感器上盖着一层**拜耳滤镜**（Bayer filter，柯达工程师 Bryce Bayer 1976 年的专利）：每个感光点上方只有红、绿、蓝其中一种滤片。2×2 为一组，**绿色占一半，红、蓝各占四分之一**。（百科）
- 为什么绿色最多？因为人眼对亮度细节最敏感的波段靠近绿色，Bayer 本人的说法就是用两倍的绿来模仿人眼。（百科）**这又回到了 2.1：连相机的设计都是围着人眼转的。**
- 结果：每个像素只真正测到一个数，另外两个是根据周围像素**猜**出来的。这一步叫去马赛克（demosaicing）。
- 可上屏的说法："你照片里的颜色，三分之二是手机算出来的。"（简化：严格说是每个像素三个数里有两个是插值得到的。上屏用"算出来的"比"猜出来的"更准确，也不显得夸张。）
- 风险：少数传感器不用拜耳排列（比如富士 X-Trans、四合一像素），但原理相同。上屏不说"所有相机"，说"你手机里的相机"或"大多数相机"。

### 2.4 亮度：给每个数加上同一个值 ★★

- 最简单的做法：R、G、B 都加上同一个值。（简化：实际软件的"亮度"多用曲线，尽量保护亮部；"曝光"更接近乘法。）
- **过曝 = 截断**：加完超过 255 的部分一律变成 255。比如本来是 240 和 250 的两个像素，都加 20 之后都变成 255，**两个原本不同的数变成了同一个数**，再调暗也分不开了。这就是"天空死白，后期救不回来"的原因。★★★
- 欠曝的暗部其实也有同样的问题（低于 0 截断成 0），但暗部通常还留着一点数据，只是噪点多。所以对 JPEG 来说"宁可稍暗，不要过曝"是一个可用的经验。（注意：拍 RAW 的摄影师流行"向右曝光"，即在不过曝的前提下尽量亮。上屏只说"别让亮部顶到头"，不说"越暗越好"。）
- 生活入口：`bad-overexposed.jpg`，海边天空一片死白。

### 2.5 对比度：绕着中间灰拉伸 ★★

- 最简单的做法：新值 = (原值 − 128) × k + 128。k > 1，亮的更亮、暗的更暗；k < 1，整体发灰。（简化：真实软件多用 S 形曲线。）
- 拉太猛，两头同时顶到 0 和 255，亮部、暗部的细节一起丢失。
- 画面：一排数字以 128 为中心向两边散开。

### 2.6 曲线：前面所有滑块都是同一种东西 ★★★（主体 A 的高潮）

- 把"输入值 → 输出值"画成一条线：
  - 什么都不调 = 对角直线
  - 加亮度 = 整条线往上平移，顶部被压平（这就是过曝）
  - 加对比度 = 线变陡
  - S 形曲线 = 柔和的对比度
- 结论："亮度、对比度、高光、阴影，本质上都是同一条曲线的不同弯法。"
- 生活入口：`bad-backlit.jpg`，逆光人脸发黑。只提亮暗部（曲线左下角往上抬），天空不动，这就是"阴影"滑块。

### 2.7 直方图（可选）★

- 把 0–255 每个值有多少像素画成柱状图。过曝的照片右边会堆出一根柱子，那就是一堆被截成 255 的像素。
- 很多手机相机的专业模式里能看到直方图，可以作为拍照建议之一，但不强求。

### 2.8 饱和度：离灰色有多远 ★★★

- 先求出这个像素对应的灰（它的亮度），再看 R、G、B 离这个灰有多远。最简单的做法：新值 = 灰 + (原值 − 灰) × s。s = 0 就是黑白，s > 1 就更鲜艳。（简化）
- **黑白照片不是三个数取平均**：标准算法里绿的权重最大、蓝的最小。比如老电视标准 Rec.601 的权重是 0.299 R + 0.587 G + 0.114 B，现代高清标准 Rec.709 是 0.2126 / 0.7152 / 0.0722。（教材）原因还是人眼对绿最敏感。★★ **第三次回到人眼**，片子可以用这一点做呼应。
- 饱和度拉满：数字被推到 0 或 255，颜色溢出，肤色发橙，色块失去层次。
- **自然饱和度（Vibrance）**：对本来就不鲜艳的颜色加得多，对已经很鲜艳的颜色加得少，很多软件还会保护肤色。拍照建议："想要鲜艳，优先拖自然饱和度。"（教材；具体算法各家不同，上屏只讲行为）

### 2.9 白平衡：给三个数各乘一个系数 ★★★（主体 B 的高潮候选）

- 光源本身有颜色。色温用开尔文（K）表示：钨丝灯约 2700–3200 K，偏橙黄；正午日光约 5500 K；阴天、阴影更高，偏蓝。（教材）
- 反直觉的一点：**K 值越高，光越偏蓝。** 但软件里的"色温"滑块往右拖，照片却变黄、变暖，因为滑块是在补偿光源的颜色。上屏不要同时出现 K 值和滑块方向，免得观众混淆。
- 人在暖光的屋子里不觉得发黄，是因为大脑会自动扣掉光源的颜色，这叫**色彩恒常性**。相机没有大脑，只能猜。
- 校正的最简单做法：找一个本该是白色或灰色的东西，把它的 R、G、B 拉平，然后把这三个系数乘到所有像素上。（教材：von Kries 式的通道增益）
- 生活入口：`bad-yellow.jpg`，晚上在家吃饭，白盘子拍成了黄的。拍照建议："拍之前点一下画面里白色的东西"（很多手机相机的专业模式能手动设白平衡），或者后期拿白色物体做参考。
- **可选彩蛋：2015 年的"蓝黑还是白金"裙子。** 裙子实际是蓝黑色。纽约大学 Wallisch 调查了约 1.3 万人，发现认为裙子在阴影里（阴影偏蓝，大脑减掉蓝）的人更容易看成白金；认为是在人造暖光下（减掉黄）的人更容易看成蓝黑。（学术）这正好说明"大脑在悄悄做白平衡"。版权提醒：不能直接用原图，可以自己画一件条纹裙子来示意。时长不够就砍掉。

### 2.10 滤镜 = 一张查找表（LUT）★★★

- 前面讲的每一条规则都是"一个数 → 一个数"。滤镜更进一步，是"一组三个数 → 另一组三个数"，可以做到"只把蓝色往青色推、肤色不动"这种效果。
- 1670 万种颜色太多，没法一一列表。常见做法是只存一张 33×33×33 的网格（35,937 个点），中间的颜色按附近格点插值。（教材；17³、33³、65³ 都常见，上屏不写具体格数，或者只说"几万个格子"）
- 所以"胶片风""日系"这些滤镜，本质上都是一张换色表，有的还额外加了颗粒和暗角。
- 回扣主线：一张照片 = 一堆数字，调色 = 改数字，滤镜 = 一份写好的改法。

## 3. 推导链总览（一屏版，供第二阶段对照）

```
光 ─→ 3 种感色细胞 ─→ 3 个数够了（屏幕上没有黄色）
                     │
                     ├→ 相机：每格只测 1 个，另外 2 个靠算（绿的最多，因为人眼）
                     ↓
          照片 = 几千万个数字（0–255）
                     ↓
      亮度 = 加 ── 过曝 = 截断（救不回来）
      对比度 = 绕 128 拉伸
      ↓
      曲线：以上都是"一个数 → 一个数"
                     ↓
      饱和度 = 离灰多远（灰怎么算？绿权重最大，因为人眼）
      白平衡 = 三个数各乘一个系数（大脑一直在自动做）
                     ↓
      滤镜 = "三个数 → 三个数"的查找表
                     ↓
      回到主图：调好 → 三条拍照建议
```

## 4. 故事素材（按"上屏价值"排序）

### 4.0 "5000 万像素"的真相（用户提议的开场，2026-10-13）★★★
- 很多手机的 4800 万 / 5000 万像素传感器是"四合一"（Quad Bayer）：相邻 4 个感光点共用同一种颜色滤片。默认模式把 4 个合成 1 个，输出约 **1250 万像素**（5000 万的常见输出尺寸是 4080×3072 = 12,533,760）。1.08 亿像素是九合一，输出约 1200 万；2 亿像素是十六合一，输出约 1250 万，另有 5000 万模式。（百科 / 科技媒体：Android Authority、AnandTech）
- 观众可以**打开相册看照片详情自己验证**，这是这个钩子最强的地方。
- **不能说"都是假的"或"骗局"**：传感器上确实有那么多感光点；合并是为了暗光下画质更好；全像素模式也真实存在，只是在大多数情况下细节提升不大。上屏用"默认""很多手机"，不点品牌（例如 iPhone 15 以后的 4800 万主摄默认输出 2400 万，不符合"1250 万"的说法）。
- 接到推导链：→ 而且每个像素只量了一种颜色（拜耳），剩下的是算出来的 → 为什么三种颜色就够？→ 人眼。

## 5. 不要用的流传说法

| 流传说法 | 问题 |
|---|---|
| "人眼能分辨 1000 万种颜色" | 估计值从约 100 万到上千万都有，来源不一，不上屏 |
| "1670 万色比人眼能看到的还多" | 跟上一条的估计挂钩，也不严谨，不上屏 |
| "皮皮虾有 12–16 种感光细胞，看到的颜色比人多得多" | ✗ 2014 年 Thoen 等人在 Science 上的实验显示，它们分辨相近颜色的能力反而不如人。不要拿来当"更多细胞 = 更多颜色"的例子 |
| "三种视锥分别感受红、绿、蓝" | ✗ 不准确：L 视锥的峰值在黄绿色。上屏只说"三种" |
| "RGB 是人类规定的标准" | 半对：具体选哪三个原色是规定的，"三个"这个数是由人眼决定的 |
| "亮度滑块就是给每个数加一个值" | 简化：只能说"最简单的做法"，真实软件用曲线 |
| "色温越高越暖" | ✗ 光源 K 值越高越蓝；滑块方向是补偿，正好反过来 |
| "过曝只要后期拉回来就行" | ✗ 已截断的部分信息永久丢失（RAW 的宽容度高一些，但传感器饱和的部分同样没了） |
| "拍照越暗越好" | ✗ 暗部有噪点。说"别让亮部顶到头" |

## 6. 反方与复杂性（脚本至少用一条，保持中立）

- **真实软件远比这复杂。** 亮度和对比度用的是曲线，很多运算是在线性光空间里做的，而不是直接改 0–255 的数（伽马）。片子讲的是"最简单的做法"和"本质"，可以在某个画面角落用小字注明"简化演示"。
- **色彩恒常性不全是好事。** 正是因为大脑会自动校正，我们才会在现场觉得"颜色挺正"，拍出来却发黄。相机反而比眼睛"诚实"。
- **"好看"没有标准答案。** 原理能告诉你每个滑块在做什么，但不能告诉你调成什么样才对。结尾可以落在"知道原理之后，审美是你自己的"。

## 8. 视觉素材方向（横屏 · 供第三阶段参考）

**整体基调：** 明亮、干净、带一点"实验室 / 显微镜"感。主角是那张早餐照片，以及从它身上放大出来的数字。**不要紫色，粉色不能偏洋红**（用户硬性要求）。

**两种"质感"交替：**

| 层 | 是什么 | 怎么做 |
|---|---|---|
| 照片层 | 主图 hero.jpg 和三张坏照片，真实、温暖 | 用 canvas 实时对真实像素做运算：亮度、对比度、饱和度、白平衡、LUT 全部真算，数字跟画面严格对应 |
| 数字层 | 放大后的像素格子、0–255 的数字、曲线图、直方图 | 等宽字体；三通道用红、绿、蓝，但要调得柔和（红偏珊瑚、蓝偏天蓝），避开紫色 |

**核心画面：**
1. **开场**：一个橙子 → 镜头推进，穿过屏幕，变成一排红绿蓝的发光小条 → 字卡"屏幕上，没有一个黄色的点。"（0–3 秒就要进入放大动作）
2. **像素放大**：主图 → 马赛克 → 一格 → 格子里跳出 `R 232 G 148 B 61`
3. **拜耳网格**：格子变成红绿交替的棋盘，每格只亮一种颜色 → 缺的两个数从邻居那里"流"过来
4. **滑块 + 数字联动**：画面下方一根滑块，拖动时上方像素格子里的数字同步变化，旁边的照片同步变化
5. **过曝**：两个格子 240、250 → 都变成 255 → 往回拖，它们一起回到 235，再也分不开
6. **曲线**：一条对角线，被拖成平移、变陡、S 形，每种形态旁边贴着对应的滑块名
7. **白平衡**：黄色晚餐照片 → 点白盘子 → 三个系数出现 → 整张照片恢复
8. **LUT**：一个三维小方块网格转动，颜色从一格流向另一格 → "胶片风"字样
9. **结尾**：主图从平淡版一步步合成最终调好的版本，叠上三条拍照建议

**素材：**
- 照片：`第五期/gen-photos/`（Codex 生成）
- 屏幕子像素、拜耳网格、曲线、直方图、LUT 方块：全部用代码画（SVG / canvas）

## 9. 进入第二阶段前的问题

1. **开场钩子**，二选一：
   - A. "屏幕上，没有一个黄色的点。"（推荐：最能直接体现"第一性"，观众能马上自己验证）
   - B. "你照片里三分之二的颜色，是手机算出来的。"（更有冲击力，但放到 38.34 当第一个高点更合适）

3. **直方图**：要不要讲？我的建议是不讲，160 秒放不下，留到评论区或者下一期。
4. **结尾**，三选一：
   - A. 三条拍照建议直接上屏（实用，方便收藏）

   - C. A + B：建议在前，金句收尾（推荐）
